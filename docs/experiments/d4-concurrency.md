# D4 동시 주문 제어 방식 비교 실험

세 가지 동시성 제어 방식을 같은 시나리오로 돌려 정확성, 처리 시간, 재시도 횟수를 비교했습니다.

- 실험 코드: `src/test/java/com/motu/experiment/` (`@Tag("experiment")`라서 평소 테스트와 CI에서는 돌지 않습니다)
- 실행 방법: `./gradlew test -Pexperiments --tests com.motu.experiment.ConcurrencyStrategyExperiment`

## 방식

세 방식 모두 주문 → 지갑 → 원장 → 보유 → 체결이라는 같은 SQL 작업을 JdbcTemplate로 합니다. 다른 것은 동시성 제어뿐이고, 체결 트랜잭션은 모두 READ COMMITTED입니다.

| 방식 | 핵심 |
| --- | --- |
| A 비관적 락 | 지갑을 `SELECT ... FOR UPDATE`로 잠근 뒤 읽고, 판단하고, 씁니다. 운영 코드(`OrderExecutor`)와 같은 방식입니다 |
| B 낙관적 락 | 잠그지 않고 읽은 뒤 `UPDATE ... WHERE version = ?`로 씁니다. 바뀐 행이 0이면 처음부터 다시 합니다(0~2ms 무작위 대기). version 컬럼은 실험용 마이그레이션(`db/experiment`)에만 있습니다 |
| C 조건부 UPDATE | `UPDATE wallets SET cash = cash - ? WHERE cash >= ?`처럼 조건을 WHERE에 넣습니다. 보유는 `INSERT ... ON DUPLICATE KEY UPDATE`로 늘리고 조건부 `DELETE`/`UPDATE`로 줄입니다. 같은 키는 주문을 먼저 INSERT해서 UNIQUE 제약으로 막습니다 |

## 환경

- Claude Code 클라우드 컨테이너, Testcontainers `mysql:8.4`, HikariCP 기본 풀(10)
- 스레드를 모두 준비시킨 뒤 `CountDownLatch`로 한꺼번에 출발시키고, 출발부터 마지막 완료까지의 시간을 쟀습니다
- 시나리오마다 방식별로 예열 1회를 버리고 5회 측정했습니다. 시간에 따른 편향을 줄이려고 A, B, C를 번갈아 돌렸습니다

- **정확:** 체결·거절 수, 잔고, 원장 합계 = 잔고, 보유 수량·원가, 주문 수가 모두 기대값과 같았던 횟수입니다.
- **재시도:** 낙관적 락에서 충돌로 처음부터 다시 시도한 횟수를 한 번 실행 전체로 더한 값입니다.

## 해석

- 세 방식 모두 네 시나리오에서 정확했습니다. 차이는 시간과 재시도에서 났습니다.
- **한 회원에게 주문이 몰릴 때(S1):** C가 가장 빠르고(A 대비 약 23% 짧음), B는 A의 약 2.6배 걸렸습니다. B는 한 행을 두고 경합하는 동안 재시도가 한 번 실행에 수백 번(중앙값 845) 났습니다.
- **경합이 없을 때(S4):** 셋이 거의 같습니다(307~353ms). 비관적 락은 같은 회원끼리만 줄을 세우므로 다른 회원의 주문은 막지 않습니다.
- **모의투자에서 한 회원이 동시에 수십 건을 보내는 경우는 드뭅니다.** S1은 최악의 상황을 일부러 만든 시나리오입니다.

## 한계

- 한 대의 컨테이너에서 한 번 측정한 값입니다. 절대값보다 방식 사이의 차이를 보는 용도입니다.
- C에서는 매도 실현손익을 계산하지 않았습니다. 줄어든 원가를 알려면 업데이트 전에 읽어야 하는데, 그러면 잠금이 필요해져 A와 비슷해집니다.
