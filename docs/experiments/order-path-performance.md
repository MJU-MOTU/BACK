# 주문 경로 성능 조사 (2026-10-30)

D4 실험([d4-concurrency.md](d4-concurrency.md))에서 같은 비관적 락인데 운영 `OrderService`가 JdbcTemplate 실험보다 훨씬 느려 보였습니다. 그 원인을 찾은 기록입니다.

- 측정 코드: `src/test/java/com/motu/trading/OrderServiceTimingExperiment.java` (`@Tag("experiment")`)
- 실행: `SEQUENTIAL=true NOISY=true ./gradlew test -Pexperiments --tests com.motu.trading.OrderServiceTimingExperiment --rerun`
- 환경: 클라우드 컨테이너, Testcontainers `mysql:8.4`, Hikari 풀 10. 이 환경은 실행마다 편차가 커서, 기준(main)과 개선을 번갈아 두 번씩 쟀습니다

## 1. 비교부터 다시

- 처음 비교한 "운영 4.6초"는 JUnit이 보고한 테스트 전체 시간이었습니다. 회원 가입(BCrypt), 가격 설정, 스레드 생성까지 들어 있었습니다.
- 같은 방식(출발 → 마지막 완료)으로 다시 재니 중앙값 약 2.3초였습니다. 실험 A(0.7초)의 약 3배입니다.

## 2. 첫 가설: 커넥션 풀 고갈 → 일부만 맞음

- 한 회원 150건을 동시에 보낼 때, 커넥션을 기다린 스레드가 최대 약 140개였습니다(풀은 10개).
- 그런데 한 스레드로 150건을 차례로 넣어도 2.2~2.9초로, 동시 실행과 비슷했습니다. 느린 원인은 경합이 아니라 **주문 1건 자체의 비용**(약 15ms)이었습니다.

## 3. 원인: 주문 1건에 MySQL 문장 30개, 그중 16개가 `SET`

`SHOW GLOBAL STATUS`의 카운터를 주문 150건 전후로 비교했습니다.

| | Questions | SELECT | INSERT | UPDATE | SET | COMMIT |
| --- | --- | --- | --- | --- | --- | --- |
| 기준 | 30.3 | 6.7 | 2.3 | 1.3 | **16.0** | 4.0 |
| 연결 설정만 바꿈 | 19.3 | 5.7 | 2.3 | 1.3 | 6.0 | 4.0 |
| 연결 설정 + 준비 트랜잭션 합침 | **11.3** | 5.7 | 2.3 | 1.3 | **0.0** | **2.0** |

주문 1건이 트랜잭션을 4개 열었습니다(같은 키 확인, 종목 확인, 시세, 체결). 그때마다 드라이버가 autocommit, read-only, 격리 수준을 바꿨다 되돌리는 `SET`을 보냈습니다.

## 4. 개선

| 이름 | 내용 |
| --- | --- |
| 연결 설정 | Hikari `auto-commit=false` + Hibernate `provider_disables_autocommit`, `transaction-isolation=READ_COMMITTED`(체결 트랜잭션이 쓰는 값을 기본으로), Connector/J `useLocalSessionState` 등 |
| 준비 트랜잭션 합침 | 잠금 전 단계(같은 키 확인 → 종목 확인 → 시세)를 `OrderPreparation` 트랜잭션 하나로 묶음. 주문 1건의 트랜잭션이 4개에서 2개로 줄어듦 |
| JVM 잠금 | `UserOrderLocks`: 같은 회원의 주문을 커넥션을 빌리기 전에 서버 안에서 먼저 줄 세움(회원 ID를 1,024개 잠금에 나눠 배정). DB 잠금은 그대로 두어 서버가 여러 대여도 정확성은 DB가 지킴 |

## 5. 결과 (기준 → 개선, 두 번 잰 중앙값)

| 항목 | 기준 | 개선 |
| --- | --- | --- |
| 주문 1건당 MySQL 문장 | 30.3 | 11.3 (−63%) |
| 순차 150건 | 약 2.8초 (2,729 / 2,901ms) | 약 1.6초 (1,715 / 1,496ms), −43% |
| 한 회원 동시 150건 | 약 2.3초 (2,228 / 2,389ms) | 약 2.0초 (2,085 / 1,849ms), −14% |
| 커넥션 대기 스레드 최대 | 약 140 | 약 9 |
| **한 회원이 150건을 보내는 동안 다른 회원 20명의 지연 (중앙값 / 최대)** | **1,095ms / 1,384ms** | **47ms / 72ms** |
| 위 항목에서 JVM 잠금만 뺐을 때 | | 894ms / 985ms |

- 한 회원의 동시 주문은 어차피 하나씩 체결되므로 개선 폭이 작습니다(−14%).
- 다른 회원이 덜 기다리게 된 것은 JVM 잠금 덕분입니다. 이게 없으면 한 회원이 잠금을 기다리는 동안 커넥션 10개를 붙잡아, 다른 회원 주문까지 줄을 섭니다.

## 6. 함께 찾은 버그

체결 트랜잭션 안의 같은 키 재확인(`OrderReplays.find`)은 처음 결과가 거절이면 예외를 던집니다. 그런데 기본 롤백 규칙 때문에 바깥 트랜잭션이 롤백 전용으로 표시됐고, 바깥이 커밋하다 `UnexpectedRollbackException`(500)이 났습니다.

- 재현: 잔고 부족 주문을 같은 키로 10건 동시에 보내면 3번 중 3번 재현됐습니다.
- 수정: `noRollbackFor = BusinessException.class`를 붙였습니다.
- 회귀 테스트: `OrderConcurrencyTests.거절될_주문을_같은_키로_동시에_보내도_모두_같은_거절을_받는다`
